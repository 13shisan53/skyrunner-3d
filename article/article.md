## 一、为什么不用引擎

我一开始想的是 Unity。想了十分钟就放弃了：一个 WebGL 小游戏，为了它装 10GB 编辑器、配构建管线、处理 WebGL 导出体积，收益是负的。

`three.js` 解决的是我真正需要的那部分——渲染、材质、光照、后期。剩下的东西，一个平台跳跃游戏需要的其实不多：

- 一个角色控制器（自己写，因为手感参数必须能一行行调）
- 一套 AABB 碰撞（自己写，引擎的角色控制器太重，改不动）
- 一个关卡生成器（自己写，二十行）
- 一个音乐调度器（自己写，因为没有音频文件）

最后 `src/main.js` 是 1057 行，`index.html` 190 行。three.js 本身是 1.2MB 的 module，本地化放进仓库，运行时不依赖任何 CDN。

## 二、手感：三个参数决定"跳起来像不像游戏"

这是整个项目里最值得写的一段。同样一个"跳"，参数不同，出来的东西完全不是一个物种。

新手做法是：按下空格 → `vy = 10`；松开 → 停。这样做的游戏，跳起来像一块砖。

真正让跳跃"跟手"的是三件事：

**1. 土狼时间（coyote time）**

你刚走出平台边缘的 0.1 秒内，系统仍然认为你站在地上。人类反应有延迟，玩家明明觉得"我踩到了边缘"，代码却判定"已经悬空"，于是跳不出来——这是最常见的挫败感来源。

```js
if (player.grounded) player.coyote = 0.11;
else player.coyote = Math.max(0, player.coyote - dt);
```

**2. 跳跃缓冲（jump buffer）**

你在落地前 0.12 秒按了空格，落地瞬间自动补上这一跳。玩家不需要精准地在落地那一帧按键。

```js
if (input.jumpPressed) player.buffer = 0.12;
player.buffer = Math.max(0, player.buffer - dt);

if (player.buffer > 0 && player.coyote > 0) {
  player.vel.y = 12.6;
  player.buffer = 0;
  player.coyote = 0;
}
```

**3. 可变跳跃高度 + 下落重力加成**

按住空格跳得高，轻点跳得矮；上升时重力 34，下落时重力 46。下落更快，落地更干脆，不会有"飘在空里"的感觉。

```js
const g = player.vel.y < 0 ? 46 : 34;   // 下落更重
if (!input.jumpHeld && player.vel.y > 0) {
  player.vel.y -= 12.6 * 0.45 * dt * 9; // 松手就截断上升
}
```

这三段加起来不到 20 行，但它决定了这个游戏"能不能玩"。参数我调了一晚上，`gravity=34 / jump=12.6 / 最大速度=8.4` 这组数字是我试出来的手感点，换一组就完全变味。

## 三、碰撞：一个顺序错误就能让你从平台上掉下去

这是我在这个项目里踩得最深的坑，也是我最想写出来的一段。

角色是一个 AABB 盒子，碰撞按轴分别解算。最初的写法很自然：先解 X，再解 Z，最后解 Y（地面）。

**这个顺序是错的，而且错得很隐蔽。**

因为重力每一帧都在把角色往下拽，角色实际上每帧都会"陷进"平台表面 1 毫米左右。当它陷进去的一瞬间，X/Z 的解算会发现"盒子与平台重叠了"，于是判断你撞到了墙，把你从平台侧面推出去——你明明站在平台中间，却被凭空推下了边缘。

表现是：走着走着突然掉下去，偶尔发生，很难复现。

修复方法就一行——**先解竖直方向，再解水平**：

```js
player.pos.y += player.vel.y * dt;
resolve('y');            // 先把脚放回地面
player.pos.x += player.vel.x * dt;
resolve('x');            // 此时不再与地面重叠
player.pos.z += player.vel.z * dt;
resolve('z');
```

落地时把角色放到 `platformTop + halfHeight + 0.001`，留 1 毫米的安全间隙，避免浮点数相等导致的二次判定。

这个 bug 我是在写完自动化测试之后才定位的：测试报告里 `afterMove.y = -2.68`——角色在水平移动 2.5 米后，竖直坐标掉到了平台下面。没有这个断言，我大概率会以为是"手感问题"而去乱调参数。

## 四、无尽关卡：生成与回收

无尽模式的核心不是"一直往前"，而是"永远只在内存里保留附近的一段"。

```js
function addSegment() {
  const diff = Math.min(1, index / 45);              // 难度曲线封顶
  const w = lerp(9, 4.4, diff) * rand(0.92, 1.08);   // 平台从 9 米缩到 4.4 米
  const gap = lerp(2.0, 4.3, diff) + rand(0, 1.0);   // 间隙从 2 米拉到 4.3 米
  const x = clamp(nextX + rand(-4.2, 4.2), -9, 9);   // 左右蛇形
  const z = nextZ + nextD / 2 + gap + d / 2;
  ...
}
```

生成是"够用就停"：只要最远平台还在角色前方 80 米内，就继续生成；身后 34 米以外的平台连同它的金币、无人机一起 `dispose()` 掉，几何体和材质都回收。

难度只跟序号有关，45 段之后封顶——否则跑到 500 米会变成不可能通过的跳跃。这不是巧合，是刻意的：**玩家的挫败感要来自操作，不能来自随机数**。

计分是 `10 × 米数 + 100 × 金币`，最高分存 `localStorage`。

## 五、没有美术资源，怎么让它看起来"不难看"

三条原则，按性价比排序：

**1. 圆角比贴图有用。**
所有平台都用 `RoundedBoxGeometry`，圆角半径取尺寸的 14%。方盒子看起来像原型，圆角盒子看起来像玩具。这一个改动带来的观感提升，比任何贴图都大。

**2. 颜色要有性格。**
平台用 7 色糖果色轮换（`#ff6f8f / #ffc849 / #4fd36a / #3f9dff / #9d78ff / #ff8a3d / #1fc9b4`），顶面比侧面亮一档。天空用着色器写渐变（顶部深蓝 → 中段天蓝 → 地平线暖色），配指数雾，远处的平台会自然融进天空里。

**3. 接触阴影。**
角色脚下永远有一块贴地的软阴影（一张 canvas 生成的径向渐变贴图），它会随高度变淡变小。没有它，角色看起来像"贴在屏幕上"；有它，角色才像"站在地上"。

角色本身也是纯几何体拼的：圆角盒子身体 + 球体脑袋 + 两个眼球 + 腮红 + 天线 + 会摆动的手脚。跳跃时身体纵向拉长，落地时压扁——这一点点夸张就是"卡通感"的来源。

开始界面：标题、键位提示、最高分都在一屏内，不占游戏画面。

## 六、关于背景音乐：我本来想用《花之舞》

我最初的计划是把《花之舞》放进去。写到一半我停了。

《花之舞》是 DJ OKAWARI 的作品，受版权保护。把它的旋律"翻译"成代码再放进公开仓库，和直接盗用录音在法律上是同一件事——不会因为"我是自己敲的音符"就变干净。用别人的曲子做个人项目，最坏的结果是仓库被 DMCA 下架，账号还可能受影响。

所以我改成写一首原创的。目标不是复刻那首曲子，而是那种**气质**：钢琴、五声音阶、温柔的循环。

实现是一个 88 BPM 的小型调度器：

```js
const chords = [
  [50, 54, 57, 61, 64],  // Dmaj9
  [47, 50, 54, 57, 61],  // Bm9
  [43, 47, 50, 54, 57],  // Gmaj9
  [45, 49, 52, 55, 59],  // A9
];
```

每个八分音符调度一次：钢琴琶音（三角波 + 正弦泛音，指数衰减包络）、每小节一次的 pad（锯齿波过低通）、贝斯、踩镲（噪声 buffer + 高通）。所有音色都是 WebAudio 现场合成的，仓库里没有一个音频文件。

如果你确实想用某首具体的曲子，唯一干净的路是买授权、放音频文件。这一点没有技术上的捷径。

## 七、加触屏那天，手机整页是黑的

游戏做完之后我加了手机支持：左下虚拟摇杆，右下跳跃键。桌面测试全过，手机模拟也过了——然后我截图一看，**全黑**。

排查过程是这样的：

1. 先怀疑 headless 截图有问题 → 关掉 JS 截图，正常显示 → 说明不是截图的问题，是页面本身
2. 打开 JS、什么都不做，正常；只要加上 `touch` 这个 class，立刻全黑
3. 盯着 CSS 看了两分钟，找到了原因：

```css
.touch { display: none; }        /* 本意：隐藏触屏控件 */
body.touch .touch { display: block; }  /* 本意：触屏设备才显示 */
```

JS 里是 `document.body.classList.add('touch')`。于是 `.touch` 这条规则**也匹配到了 `<body>` 自己**——整个页面 `display: none`。

真机上会是一片黑屏，玩家什么都看不到。所有"逻辑测试"都会通过，因为它测的是 JS 状态，不是像素。

改成 `.touch-ui` 就好了。这件事给我的教训不是"要小心 CSS 选择器"，而是：**能跑 ≠ 能看，必须真的截图**。

## 八、不靠"我觉得能跑"，用 CDP 跑测试

游戏的测试很尴尬：它没有返回值，也不好写单元测试。我的做法是用 Chrome DevTools Protocol 直接驱动真浏览器，对着线上地址跑：

- 移动后 `z` 是否增加、是否还站在平台上（`grounded === true`）
- 跳跃后高度是否上升
- 走到金币旁边，计数是否 +1
- 关卡是否持续生成（最远平台的距离）
- 掉下去之后，游戏结束遮罩是否出现、最高分是否写入
- 手机模拟下，摇杆和跳跃键是否可见、摇杆能否让角色移动、跳跃键是否真的让角色起跳
- 全程是否有未捕获异常或 console error

线上版本的测试结果：

```
boot     : ready=1  fatal=空  platforms=8
movement : z 0 → 2.98  grounded=true  score=20
jump     : y=1.85
coins    : 0 → 1
generate : platforms=9  newestZ=91
gameover : mode=over  overlay=true  score=200  best=200
restart  : mode=play  score=0
mobile   : touch=true  stick=true  jumpBtn=true  stickZ=1.53  jumpY 0.55→1.58
errors   : exceptions=0  console=0
```

"移动后 `grounded=true`" 这一条，就是前面那个碰撞 bug 的守卫。没有它，我永远不知道自己在修什么。

## 十、下一步

现在能玩，但离"好"还有距离。按优先级：

1. **排行榜**——本地最高分太孤独了，但没有后端就只能接 Firebase 之类的服务
2. **更多机制**——移动平台、弹簧、易碎平台，现在只有金币和无人机
3. **音乐分层**——分数越高，鼓点越密，这个投入产出比很高
4. **角色换肤**——现在只有一个角色
