## 0. 摘要与变更对照

### 0.1 一页摘要

SKYRUNNER 是一个打开即玩的 3D 无尽平台跳跃游戏，目标用户是碎片时间玩家，同时兼作开发者的作品集入口。

v3.0 的四个结论：

1. **操控可信度是当前最大缺陷**。左右方向键与屏幕方向相反 [代码]（根因见 §6.2），前进完全自动化 [代码]（`speedAt(distance)`），玩家没有"开"的决策权；这两条不修，再好的画面也留不住人。
2. **失败成本过高**。掉下去直接结束 [代码]（`events.push({type:'fall'})` → `beginDeath()`），撞到障碍只击退不扣血 [代码]（`hit()` 仅返回 `'hit'`）。挫败来自不可控事件，而不是来自操作失误。
3. **收益结构有漏洞**。金币在 2.4m 内被强制吸向玩家 [代码]（`world.js` 第 415–418 行），玩家不需要规划路线，难度曲线被自动收益抹平。
4. **"手机可玩"没有兑现为"双端互通"**。触屏 UI 已存在 [代码]（`input.js` 虚拟摇杆 + 跳跃键），但没有 PWA 离线、没有账号与云存档，PC 打的分与手机打的分彼此不可见 [代码：存档仅 `localStorage`，`STORAGE_KEY='skyrunner.save.v2'`]。

v3.0 的解法：修映射、改油门、加血条、把吸附做成道具、正式做移动端与云同步。

### 0.2 本版变更请求对照表

| 编号 | 变更请求（原始表述） | 优先级 | 本版落点 | 状态 |
|---|---|---|---|---|
| CR-1 | 游戏只能端游游玩，不能双端互通，缺少手机端使用 | P0 | §6.6 移动端与双端互通 | 规划中 |
| CR-2 | 左右方向键不对应，按左键会往右走，按右键同理 | P0 | §6.2.1 方向映射修复 | 规划中 |
| CR-3 | 前进后退应该自己操作，不能自动化 | P0 | §6.2.2 手动油门 | 规划中 |
| CR-4 | 不能自动吸附金币，可以出现类似小道具，小道具具有吸附金币能力 | P0 | §6.5 道具系统（磁铁） | 规划中 |
| CR-5 | 障碍物不仅可以移动，而且人物碰到障碍物会降低生命值 | P0 | §6.4 生命值与受击 | 规划中 |
| CR-6 | 任务拥有三格生命值，提高可能性 | P0 | §6.4 三格生命 | 规划中 |

> 6 条全部为 P0：其中 CR-2、CR-3 属于**可用性缺陷**（当前状态下游戏不可正确操作），CR-4 ~ CR-6 属于**玩法核心重定义**，CR-1 属于**触达面扩张**。P0 集中在一版，说明当前版本处于"能演示、不能玩"的阶段。

### 0.3 与 v2.1 的差异与影响面

| 维度 | v2.1 | v3.0 | 影响 |
|---|---|---|---|
| 操控 | 自动前进 + 左右平移 [代码] | 手动油门（前进/后退/滑行）+ 左右 | 输入层重写，难度曲线重排 |
| 生命 | 坠落即结束，撞障碍只击退 [代码] | 3 格生命，撞击扣血，坠落扣血后重生 | 新增 lives 模块，重生点逻辑 |
| 收益 | 金币自动吸附 [代码] | 无吸附，磁铁作为道具限时开启 | 金币分布密度与价值需重调 |
| 道具 | 仅护盾 [代码] | 5 类道具（磁铁/护盾/加速/慢动作/金币加倍） | 新增 powerup 模块与 HUD |
| 平台 | 移动端 Web 可玩，存档本地 | PWA 可离线；账号 + 云存档双端同步 | 新增同步服务（Workers + KV） |
| 包体 | 289KB 首屏 [实测] | ≤ 320KB [规划] | 同步 SDK 与 PWA 资源需克制 |
| 性能 | 软渲染 14fps [实测] | 真机 60fps 目标（手油门下渲染压力不变） | 维持 |

**变更影响分析**：CR-2、CR-3 会改变"距离"这个核心指标的分布（玩家可以停下、可以后退），计分公式 `score = floor(最大前进距离) × 10 + 金币数 × 100` [代码：`score.js`] 必须改写为"净前进距离"以防后退刷分；CR-4 改变金币获取路径，任务 `coins40` [代码：`MISSIONS`] 的达成率将下降；CR-5、CR-6 提高单局时长约 40% ~ 70%（预估 [假设]），广告位/分享点需要重新设计。

## 1. 背景与问题

### 1.1 变更请求的来源

这 6 条不是头脑风暴的产物，是实际打开游戏玩之后提出来的。具体对照：

| 变更请求 | 现象（可复现） | 现状根因（代码级） |
|---|---|---|
| CR-2 | 按 ← 角色往屏幕右跑 | 相机在 `target.z - distance` 并朝 +Z 看 [代码：`camera.js`]，故**屏幕右 = 世界 -X**；而 `input.js` 中 `ArrowRight → steer=+1`，`player.js` 直接用 `targetX = steer × 6.0`（世界 +X）[代码]，两者叠加即反向 |
| CR-3 | 角色自己一直往前跑，玩家只能左右 | `main.js` 每帧 `player.speed = speedAt(distance)`，玩家无油门 [代码] |
| CR-4 | 金币自己飞进兜里 | 金币进入 2.4m 半径即向玩家插值 [代码：`world.js` 415–418 行] |
| CR-5 | 撞到无人机不掉血 | `hit()` 只返回 `'hit'` 与无敌帧，扣血逻辑不存在 [代码：`player.js` 221–230 行] |
| CR-6 | 没有生命值概念 | 全局无 lives 状态；死亡只由 `pos.y < deathY (-18)` 触发 [代码] |
| CR-1 | 手机上能玩但进度不互通 | 存档仅 `localStorage` [代码]；无 PWA manifest / service worker；无账号 |

### 1.2 问题陈述

> **问题 A（操控不可信）**：一个要求玩家做空间决策的游戏，却把前进交给脚本、把左右搞反。玩家无法建立"我操作得好 = 我能走更远"的因果关系，重复游玩失去意义。
>
> **问题 B（失败不可控）**：除了坠落，其他失败来源不产生代价。没有血量的游戏里，撞障碍和躲障碍没有区别，躲避行为不会被内化。
>
> **问题 C（收益无成本）**：金币自动吸附使"路线规划"这一决策消失。玩家永远能吃到所有金币，难度只能靠平台尺寸硬堆，挫败感转为"运气不好"。
>
> **问题 D（触达不完整）**：碎片时间的主力场景是手机，但手机上的进度是孤岛；PC 与手机之间没有任何通路，作品集也无法展示"完整产品"的闭环。

### 1.3 现有方案为什么不够

| 现状 | 为什么不够 |
|---|---|
| Chrome 恐龙 | 2D、无空间感；且同样是"自动前进"，说明自动前进**不是**自动成功的 |
| 跳一跳 | 依赖微信生态、需下载；交互只有点击 |
| 各类 three.js 跑酷 demo | 有自动跑酷，但**没有**生命值、道具、失败代价与重开循环 |
| 主流无尽跑酷（Subway Surfers 等） | 前进自动，但左右与跳跃的操作是**高精度可控**的，且有明确的"复活/护盾"机制降低随机挫败 |

**结论**：自动前进本身不是原罪；**自动前进 + 方向不可控 + 无代价**的组合才是。v3.0 的做法是：保留"省心"，但把方向与代价还给玩家。

## 2. 目标与指标

### 2.1 v3.0 产品目标与达成标准

| 编号 | 目标 | 判定标准 | 验证方式 |
|---|---|---|---|
| G1 | 方向跟手 | 按住 → 角色在屏幕空间向左移动 ≥ 0.8m，松开 0.3s 内停下；相机旋转 90° 后仍成立 | CDP 自动化 + 人工 5 人测试 |
| G2 | 前进可控 | 松开油门键后 1.2s 内速度衰减到 0.2m/s 以下；后退速度上限 -3.0m/s | `test/e2e/feel.mjs` 扩展 |
| G3 | 失败有代价但不终结 | 撞障碍 -1 血，1.2s 无敌；坠落 -1 血并在安全点复活；0 血才结算 | E2E 逐条断言 |
| G4 | 收益靠规划 | 无道具时金币获取率 ≤ 85% 路径可覆盖；磁铁道具可把该值提到 ≥ 98% | 路径回放统计 |
| G5 | 手机正式可玩 | PWA 可安装、可离线首启；390×844 真机首屏可交互 ≤ 3.0s | 真机 3 款机型实测 |
| G6 | 双端互通 | 同一账号在 PC 与手机登录后，30s 内同步最高分/金币/角色/设置 | 双设备交叉验证 |

### 2.2 北极星指标

**单次会话的有效游玩时长**（页面可见且处于 play 状态的累计时间）。

沿用 v1.0 的选择理由：无广告、无内购、无强留存的商业化诉求，"玩了多久"是唯一同时反映**手感可信**与**难度曲线成立**的指标。v3.0 新增副指标：

- **副指标 A：单局平均生命消耗**（目标 1.6 ~ 2.4 血/局 [假设]）：反映三格生命是否把"偶发挫败"变成"可学习曲线"。
- **副指标 B：手动油门使用率**（目标 100%，即不存在无输入自动前进）[代码可验证]。

### 2.3 过程指标与阈值-动作

| 指标 | 定义 | 目标 | 低于阈值时的动作 |
|---|---|---|---|
| 首次得分率 | 进入游戏 10 秒内 score > 0 | ≥ 90% | 检查首屏与操控提示 |
| 首局时长 | 第一局从开始到结束 | 45s ~ 150s | 过长说明难度不足，过短说明惩罚过重 |
| 重开率 | 结算后点击"再来一次" | ≥ 70% | 结算面板摩擦过高 |
| 方向误操作率 | 测试者按错方向次数 / 总方向输入 | ≤ 5% | 映射仍有问题，阻断发布 |
| 同步成功率 | 登录后云存档写入成功 | ≥ 99% | 降级为本地模式并提示 |
| PWA 安装转化 | 首启后 7 天内添加到主屏比例 | ≥ 8% [假设] | 优化引导时机 |

| 编号 | 假设 | 状态 | 证伪条件 | 退出策略 |

## 3. 用户与场景

### 3.1 目标用户

**P1 碎片时间玩家（主要，手机优先）**
- 18–30 岁，通勤 / 排队 / 等电梯，手机为主
- 玩过跳一跳、Subway Surfers 类产品
- 痛点：不想下载、不想注册、不想看教程
- 关键诉求：**失败要快、重开要快、进度不能丢**

**P2 桌面休闲玩家（次要，PC 优先）**
- 办公室摸鱼或长时游玩，愿意用键盘精细操作
- 关键诉求：**操控跟手、方向不反、可以慢慢玩**
- 典型行为：会主动用方向键微调，会用 Shift/空格做精细操作

**P3 同行 / 面试官（次要但真实）**
- 从简历或文章点进来，停留 30 秒 – 3 分钟
- 关注点：这个人能不能把东西做完、文档是否可信
- 关键诉求：3 秒看出技术含量，能点开源码

> 三个用户对首屏的要求冲突：P1 要立刻能玩，P2 要不被"自动跑"糊弄，P3 要看到信息。解法不变——开始按钮是唯一焦点，技术信息在按钮下方一行（§6.8）。

### 3.2 核心用户故事

| 编号 | 场景 | 用户故事 | 关联 |
|---|---|---|---|
| US-1 | 地铁上单手玩 | 作为通勤用户，我想一只手完成转向、用另一只手控制前进与跳跃，这样我抓着扶手也能玩 | CR-3、CR-1 |
| US-2 | 第一次打开 | 作为新用户，我想在 10 秒内知道"要干什么"，并且知道"撞到东西会掉血" | CR-6 |
| US-3 | 撞到障碍 | 作为玩家，我想清楚地看到血少了一格，并且有一小段时间无敌，这样我知道是我操作失误而不是游戏随机 | CR-5、CR-6 |
| US-4 | 想要金币 | 作为玩家，我想通过绕路或者捡道具来拿金币，而不是金币自己飞进来，这样"贪一点还是稳一点"是我的选择 | CR-4 |
| US-5 | 换设备 | 作为玩家，我想在电脑上打的分在手机上能看到，这样我的进度是连续的 | CR-1 |
| US-6 | 失败后 | 作为玩家，我失败后想立刻再来一局，复活后 1.5 秒内不想被再次撞死 | CR-5 |
| US-7 | 挑战自己 | 作为玩家，我想看到自己的最高分、收集到的角色与特效，以便有目标地重玩 | CR-1 |
| US-8 | 评估开发者 | 作为面试官，我想快速判断这个项目的技术深度，并能看到源码和 PRD | — |

### 3.3 我们不服务谁

- 硬核动作玩家（需要精确连招、长时间练习）
- 多人 / 社交对战玩家
- 付费深度玩家（无内购、无抽卡）
- 需要离线购买客户端的原生 App 用户（但 PWA 可添加到主屏）

## 4. 方案与取舍（决策记录）

### 4.1 六条变更的设计决策

| 编号 | 决策 | 理由 | 代价 | 被否决的备选 |
|---|---|---|---|---|
| CR-2 | 输入层输出**屏幕空间**语义（`steer=+1` 恒表示"视觉向右"），由 `player.js` 换算到世界坐标 | 保留相机自由旋转；语义在唯一一处换算，可单测 | 需改 `input.js` + `player.js` + 触屏摇杆三处 | 直接翻转 `input.js` 符号：相机旋转 90° 后又会反，治标不治本 |
| CR-2' | 增加"相机朝向指示"：屏幕底部显示当前前进方向的小箭头 | 手动油门 + 自由相机下，用户容易迷失朝向 | 增加一点 HUD | 锁死相机朝向：牺牲自由度，否决 |
| CR-3 | 引入**油门（throttle）**状态：按住前进键加速到上限，松开按惯性滑行，减速键可后退至 -3.0m/s | 恢复"开"的决策权，且保留碎片场景的省心（默认滑行不倒退） | 难度曲线不能再靠速度自动提升，需改为关卡密度驱动 | 保留自动前进、只加减速：等于半自动，CR-3 未被满足，否决 |
| CR-3' | 速度上限改为**按距离解锁**：基础 6.8m/s，每 120m +0.6m/s，封顶 10.8m/s | 手动驾驶下若不封顶，玩家可用"停在安全平台等解锁"拖时间 | 需要为停等设计压力机制（远处障碍推进） | 保持固定 10.8m/s：速度感过强，与手动控制不匹配 |
| CR-4 | 移除 2.4m 自动吸附；**磁铁**作为限时道具提供吸附（半径 6m / 8s） | 把"白送的收益"变成"争取来的收益"，与 CR-3 决策哲学一致 | 金币路径需重排，否则道具价值感弱 | 保留自动吸附并调小半径：违背"不要自动"的核心诉求，否决 |
| CR-5 | 障碍（无人机）碰撞 = 扣 1 血 + 击退 + 1.2s 无敌 + 短暂慢镜反馈；踩踏仍可消灭它 | 让躲避成为有代价的决策，同时保留"技术解法"（踩） | 需要血量状态与反馈 | 碰撞即死：与 CR-6 冲突，否决 |
| CR-6 | **3 格生命**；坠落 = 扣 1 血并在最近安全平台复活（1.5s 无敌）；血量归零才结算 | 把"随机失败"变成"可承受的失败"，提高单局时长与重开率 | 需要复活点搜索与防卡死逻辑 | 坠落仍然直接结束：只做半条，否决 |
| CR-1 | 移动端 = PWA（manifest + service worker 离线可玩）；双端互通 = **可选账号**（GitHub OAuth / 邮箱魔法链接）+ 云存档（Workers + KV） | 静态托管下唯一能同时满足"零安装"与"跨端"的组合；账号可选保住碎片场景不流失 | 引入后端依赖，违背 v1.0"零依赖"原则 | 原生 App：与"打开即玩"直接冲突；纯本地存档（v2.1 现状）：无法互通，否决 |

### 4.2 被否决的方案（补充）

| 方案 | 否决理由 |
|---|---|
| 把方向键直接与 `vel.x` 取反 | 只修好默认相机朝向；玩家用鼠标转视角后立刻复发 |
| 用"自动前进 + 玩家只能左右"继续做 v3.0 | CR-3 明确要求"前进后退自己操作"，半自动不满足需求 |
| 磁铁做成永久能力 | 收益永久化后等同于自动吸附，只是换了名字 |
| 生命值做成"血条数值"（100 血） | 碎片场景下玩家读不出 100 血里掉了 17，三格心形是更低认知成本的选择 |
| 引入排行榜/社交（v1.1 原计划） | 与 CR-1 的账号成本叠加，v3.0 应先做"单账号跨端"最小闭环 |
| 用同一套 HUD 同时服务手机与 PC | 手机竖屏宽度不足以同时容纳油门、跳跃、血量与分数，需要差异化布局（§6.6.3） |

### 4.3 取舍共同指向的产品形态

三条主线合起来是同一件事：**把控制权、代价与收益都还给玩家**。

- 控制权：方向与油门都归玩家（CR-2、CR-3）
- 代价：失败消耗有限资源而不是直接终止（CR-5、CR-6）
- 收益：靠规划与道具获得，而不是自动到账（CR-4）
- 触达：把这套体验完整地送到手机，并与桌面连通（CR-1）

**一句话定义 v3.0**：*从"自动跑的演示"变成"开得动的游戏"。*

### 5.3 变更流程（含量化预算）

- **首屏预算**：≤ 320KB [规划]（v2.1 实测 289KB [实测]），超出即不允许合并；
- **单次额度**：一个版本最多引入 3 个新依赖；PWA 资源与同步 SDK 合计 ≤ 25KB（gzip 后）；
- **性能红线**：中端手机 390×844 上连续 60s 无长帧（>50ms）超过 2 次；
- **离线可用**：断网后至少可完整游玩 1 局；
- **无障碍**：不新增任何仅靠颜色区分的信息（生命用形状 + 数字，激活道具用图标 + 计时条）。

### 5.4 Definition of Done

一条需求算"完成"，必须同时满足：

1. 代码合并到 `main`，无 console error / 未捕获异常（自动化断言 0/0）；
2. 有对应的自动化用例（单元或 E2E），且在 CI 通过；
3. 本文档对应条目从 `[规划]` 改为 `[代码]`，并写明实现位置（文件 + 常量名）；
4. 若涉及数值，给出改动前后的对比与来源标注；
5. 若涉及用户可见文案，`src/strings.js` 中 zh-CN 与 en 同步更新（i18n 键一一对应）；
6. 线上验证通过（不是"本地觉得没问题"），并记入 §12 验收清单；
7. 无新增 P0/P1 技术债；若必须新增，登记到 §8.3 矩阵。

## 6. 产品规格

优先级：**P0 = 缺失则本版不成立；P1 = 显著影响体验；P2 = 加分项。** 全部条目默认状态为 `[规划]`。

### 6.1 核心循环（v3.0）

**一句话**：*玩家自己开车，自己躲，撞了掉血，血掉光才算结束；金币要绕路或用道具才拿得到。*

```
准备（首屏 1 个主按钮）
  → 开局（3 格生命 / 油门在中位 / 0 道具）
  → 驾驶（左右转向 + 油门前进 + 跳跃）
      ├─ 吃到金币（+分，路线偏离才有增量）
      ├─ 捡到道具（磁铁/护盾/加速/慢动作/加倍，限时生效，HUD 显示倒计时）
      ├─ 撞到障碍（-1 血 + 击退 + 1.2s 无敌 + 连击中断）
      └─ 坠落（-1 血 + 在安全平台复活 + 1.5s 无敌）
  → 血量归零 / 主动退出
  → 结算（分数、距离、金币、最高连击、剩余生命、死因、同步状态）
  → 再来一次（无加载） / 同步进度
```

与 v2.1 的关键差异：**循环里第一次出现了"资源"（生命）和"工具"（道具）**，因此玩家的目标是复合的——既要活得久，又要吃得多。

### 6.3 无尽生成与难度曲线

| ID | 需求 | 验收标准 |
|---|---|---|
| F-25 | 前方始终保有可行进路径 | ≥ 60m 可行路径 [代码基线：`SEG.ahead = 80`] |

### 8.5 同步服务设计

| 项 | 设计 |
|---|---|
| 形态 | Cloudflare Workers + KV，接口：`POST /sync`（拉取+推送）、`POST /guest`（生成同步码）、`GET /health` |
| 身份 | GitHub OAuth（`/auth/github`）或邮箱魔法链接；令牌存于 HttpOnly Cookie，前端不持有长期密钥 |

| 频率限制 | 单用户 60 次/分钟；单局最多 2 次写入 |
| 失败处理 | 写失败进入本地队列（最多 20 条），下次联网按序补传；超过 24h 未同步则在 UI 标注"待同步" |
| 隐私 | 只存游戏进度与账号标识；不存设备指纹、不做行为画像；提供导出与一键删除（§9.3） |

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| 手动油门让碎片场景玩家不适应 | 高 | 中 | H1 假设退出策略：改为"惯性滑行 + 仅刹车"；5 人测试先行（V1） |
| 方向修复引入新的镜头/相机耦合 bug | 中 | 中 | 单一换算函数 + 4 个 yaw 角度的单元测试锁死 |
| 生命系统让分数虚高（刷血） | 中 | 中 | 计分改净前进；坠落扣血且不累计距离 |
| 同步服务引入后端故障面 | 中 | 中 | 同步失败静默降级本地；静态站与同步服务解耦部署 |
| 账号体系抬高进入门槛 | 中 | 中 | 账号可选；首屏不弹登录；游客同步码兜底 |
| PWA 缓存导致版本错乱 | 中 | 低 | 版本号 + 缓存策略分离；提供"有新版本"提示而非强刷 |
| 真机性能不达标 | 高 | 中 | 画质自动分级；降低粒子/云量；必要时关闭 Bloom |
| 道具数值失衡（磁铁过强） | 中 | 中 | 埋点监控磁铁期间金币占比；上限 30% 加成路径 |
| 单人维护停更 | 中 | 中 | 无构建、低依赖；每版附完整 PRD 与验收清单 |

## 13. 附录

### 13.1 术语表

| 术语 | 含义 |
|---|---|
| 土狼时间 | 离开平台后仍允许起跳的宽限时间（0.11s） |
| 跳跃缓冲 | 落地前提前按下跳跃，落地瞬间自动执行 |
| 油门（throttle） | v3.0 新增：玩家对前进/后退的输入意图，-1 / 0 / +1 |
| 惯性滑行 | 松开油门后按指数阻尼自然减速 |
| 屏幕空间语义 | 输入方向以"屏幕上的左右"定义，与世界坐标、相机朝向解耦 |
| 无敌帧 | 受击后短暂免疫再次扣血的窗口 |
| 复活点 | 坠落重生位置，必须满足前方 20m 无障碍 |
| 磁铁道具 | 限时开启金币吸附的道具（CR-4） |
| 双端互通 | 同一账号在 PC 与手机上共享游戏进度 |
| 同步码 | 游客模式下用于跨设备迁移进度的短码 |
| PWA | 可安装、可离线的渐进式网页应用 |
| 画质分级 | 按设备性能自动切换渲染档位（high/mid/low） |
| 净前进距离 | 最大前进距离减去回退距离，用于计分防刷 |
