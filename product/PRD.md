## 1. 背景与问题

### 1.1 为什么做这个产品

三个具体动机，按权重排序：

1. **验证一个技术判断**：一个手感合格的 3D 平台游戏，是否必须依赖商业引擎（Unity / Unreal）？如果用 three.js + 自写控制器可以在 1.3MB 内做到"能玩"，那么大量轻量 3D 需求（营销页、教学演示、小游戏）都不需要引入重型工具链。
2. **补一块能力短板**：我做过机器视觉项目，但缺少"从 0 到 1 交付一个用户可触达的完整产品"的经验——包括手感调优、移动端适配、上线与验证。
3. **作品集载体**：简历上的项目描述是静态的，一个能点开就玩的链接是动态的。

### 1.2 要解决的用户问题

> 在通勤、排队、等待加载的碎片时间里，用户想要"打开即玩、3 秒内理解、单手可操作"的 3D 游戏体验，但主流 3D 游戏要么需要下载数十 MB 的客户端，要么需要注册账号，要么学习成本高到碎片时间撑不住。

### 1.3 现状与机会

| 现状 | 问题 |
|---|---|
| 原生 App 游戏 | 需下载安装，冷启动 30s+，碎片场景不成立 |
| 商业引擎导出的 WebGL 包 | 首包常 5–20MB，低端移动网络加载失败率高 |
| 2D 网页小游戏（如 Chrome 恐龙） | 打开快，但缺少 3D 空间感与操作深度 |
| 3D 网页 demo | 多为技术演示，缺少计分、失败反馈、重开循环等"游戏性"闭环 |

**机会点**：`首屏 ≤ 2MB + 无需安装 + 单一操作动词（跳） + 有分数驱动重玩` 的交集目前是空的。

## 2. 目标与成功指标

### 2.1 产品目标（v1.0）

| 目标 | 判定标准 |
|---|---|
| G1 打开即玩 | 4G 网络下，从点击链接到可操作 ≤ 5 秒 |
| G2 零学习成本 | 不读说明也能在 10 秒内完成第一次跳跃与第一次得分 |
| G3 手感可信 | 内部可复现：连续 10 次跳跃落点偏差 ≤ 0.2m |
| G4 双端可用 | 桌面键鼠与手机触屏均可完成完整一局 |

### 2.2 北极星指标

**单次会话的"有效游玩时长"**（页面可见且处于 play 状态的累计时间）。

选它而不是 DAU 的原因：本产品无账号体系、无后端，DAU 无法统计；而"玩了多久"直接反映手感与难度曲线是否成立。

### 2.3 过程指标（v1.0 只能本地估算）

| 指标 | 定义 | 目标 | 现状 |
|---|---|---|---|
| 首次得分率 | 进入游戏后 10 秒内 score > 0 的比例 | ≥ 90% | 未埋点，待 v1.1 |
| 首局时长 | 第一局从开始到失败的时间 | 25–90 秒 | 未埋点 |
| 重开率 | 失败后点击"再来一次"的比例 | ≥ 60% | 未埋点 |
| 最高分分布 | 本地 best 的中位数 | 500–1500 | 未埋点 |
| 3 秒跳出率 | 打开后 3 秒内离开 | ≤ 15% | 未埋点 |

> **诚实说明**：v1.0 没有任何数据上报。上表是待验证假设，不是结论。要在 v1.1 落地最小埋点（见 §10）。

## 3. 用户与场景

### 3.1 目标用户

**P1 碎片时间玩家（主要）**
- 18–30 岁，通勤/排队场景，手机为主
- 玩过跳一跳、Flappy Bird 类产品，能接受"一局一分钟"
- 痛点：不想下载、不想注册、不想看教程
- 关键诉求：**失败要快、重开要快**

**P2 同行/面试官（次要但真实）**
- 通过简历或文章点进来，停留 30 秒–3 分钟
- 关注点不是"好不好玩"，而是"这个人能不能把东西做完"
- 关键诉求：**3 秒内看出技术含量，能点开源码**

> 这两个用户对首屏的要求冲突：P1 要立刻能玩，P2 要看到信息。解法是把"开始"按钮做成唯一焦点，技术信息放在按钮下方一行（见 §8.2）。

### 3.2 核心场景（用户故事）

| 编号 | 场景 | 用户故事 |
|---|---|---|
| US-1 | 地铁上单手玩 | 作为通勤用户，我想用一只手（左手摇杆 + 右手拇指跳）完成一局，这样我抓着扶手也能玩 |
| US-2 | 第一次打开 | 作为新用户，我想在 10 秒内知道"要干什么"，不想读说明 |
| US-3 | 失败后 | 作为玩家，我失败后想立刻再来一局，不想等加载或看广告 |
| US-4 | 挑战自己 | 作为玩家，我想看到自己的最高分，以便有目标地重玩 |
| US-5 | 评估开发者 | 作为面试官，我想快速判断这个项目的技术深度，并能看到源码 |

## 4. 竞品与定位

| 产品 | 优势 | 不足 | 我们的差异 |
|---|---|---|---|
| Chrome 恐龙 | 打开即玩、零成本 | 2D、无空间感、玩法单一 | 3D 空间 + 跳跃深度 |
| 跳一跳 | 操作极简、社交排名 | 需微信生态、无 3D 自由移动 | 不依赖平台，浏览器直达 |
| Celeste / 蔚蓝 | 手感顶级 | 需下载、硬核、学习曲线陡 | 同样的手感原则，更低的进入门槛 |
| 各类 three.js demo | 技术展示充分 | 无计分/失败/重开闭环，不像"游戏" | 完整的游戏循环 |

**定位一句话**：*浏览器里最接近"能玩"的 3D 平台跳跃，3 秒上手，一分钟一局。*

**不做的事（同样重要）**：不做账号体系、不做内购、不做多人、不做关卡编辑器。理由见 §5.3。

## 6. 功能需求

优先级定义：**P0 = 没有它产品不成立；P1 = 显著影响体验；P2 = 加分项。**

### 6.1 移动与跳跃（P0）

| ID | 需求 | 验收标准 |
|---|---|---|
| F-01 | 角色按相机朝向移动 | 相机旋转 90° 后按 W，角色朝新前方移动，偏移 ≤ 5° |
| F-02 | 地面加速 / 空中弱控制 | 地面达到最大速度 ≤ 0.25s；空中加速度为地面的 48% |
| F-03 | 土狼时间 | 离开平台边缘后 0.11s 内按跳跃仍可起跳 |
| F-04 | 跳跃缓冲 | 落地前 0.12s 内按下跳跃，落地瞬间自动起跳 |
| F-05 | 可变跳跃高度 | 轻点跳跃高度约为长按的 56%（线上实测：1.19m vs 2.13m） |
| F-06 | 下落重力加成 | 下落重力 46 > 上升重力 34，滞空感可感知 |

**数值（不可随意改动的基线）**：

| 参数 | 值 | 说明 |
|---|---|---|
| 最大跑速 | 8.4 m/s | 冲刺 ×1.35 = 11.3 m/s |
| 跳跃初速 | 12.6 m/s | 理论最大高度 2.33m，实测 2.13m（逐帧积分的离散损耗） |
| 上升重力 | 34 m/s² | |
| 下落重力 | 46 m/s² | 落地更快，减少"飘" |
| 最大下落速度 | 44 m/s | 防穿透 |
| 地面摩擦 | 11（指数衰减） | 松手 0.2s 内基本停住 |

### 6.2 无尽关卡（P0）

| ID | 需求 | 验收标准 |
|---|---|---|
| F-10 | 平台向前持续生成 | 玩家前方始终保有 ≥ 60m 的可行进路径 |
| F-11 | 身后回收 | 身后 34m 外的平台被销毁，内存不随距离线性增长 |
| F-12 | 难度随距离上升 | 平台尺寸 9m → 4.4m，间隙 2m → 4.3m，**45 段后封顶** |
| F-13 | 生成可通关性 | 相邻平台水平间距 ≤ 最大跳跃距离的 80% |

> 最大跳跃距离 ≈ 5.7m（8.4 m/s × 约 0.67s 滞空）；实际最大间隙 4.3m，约为其 75%，保留约 25% 的容错空间。
| F-14 | 高度变化受控 | 相邻平台高度差 ∈ [-1.1, +1.1] m，不超过单次跳跃高度的 50% |

**为什么难度要封顶**：无限增长的难度在第 60 段后会变成"必死"，玩家的失败归因会从"我操作不好"变成"游戏耍赖"。**挫败感必须来自操作，不能来自随机数。**

### 6.3 计分与经济（P0）

| ID | 需求 | 验收标准 |
|---|---|---|
| F-20 | 距离计分 | 每前进 1m 得 10 分 |
| F-21 | 金币计分 | 每枚金币 100 分；踩杀无人机额外 +2 金币 |
| F-22 | 最高分持久化 | 刷新页面后 best 仍保留（localStorage） |
| F-23 | 结算展示 | 失败面板显示：本局分数、距离、金币、历史最高 |

**计分公式**：`score = floor(最大前进距离) × 10 + 金币数 × 100`

**设计意图**：距离是线性收益，金币是机会收益（需要偏离最优路线），两者相乘形成"贪一点还是稳一点"的决策。

### 6.4 触屏操作（P0）

| ID | 需求 | 验收标准 |
|---|---|---|
| F-30 | 虚拟摇杆 | 左下角，触摸拖动时摇杆头跟随，松手回中 |
| F-31 | 跳跃键 | 右下角，按下即起跳，按住可跳更高 |
| F-32 | 相机拖拽 | 摇杆与跳跃键以外的区域拖动可旋转视角 |
| F-33 | 安全区适配 | iPhone 刘海/底部横条不遮挡控件（env(safe-area-inset-*)） |
| F-34 | 触屏判定 | `ontouchstart` 或 `pointer: coarse` 才显示触屏 UI |

**布局规范**：摇杆直径 132px，距左/下各 20–24px；跳跃键 96px，距右/下各 20–30px。竖屏下相机距离从 7.6m 拉到 9.6m，俯角从 0.30 提到 0.38（否则角色占据屏幕 1/3）。

### 6.5 音频（P1）

| ID | 需求 | 验收标准 |
|---|---|---|
| F-40 | 音效 | 跳跃、落地、金币、踩杀、坠落、结算各有独立音色 |
| F-41 | 背景音乐 | 88 BPM 循环，四和弦进行，无音频文件 |
| F-42 | 静音开关 | 右上角按钮，状态可见，刷新后保持 |

### 6.6 视觉（P1）

| ID | 需求 | 验收标准 |
|---|---|---|
| F-50 | 平台配色 | 7 色轮换，顶面比侧面亮一档，色彩饱和度足以区分 |
| F-51 | 接触阴影 | 角色脚下软阴影随高度变淡变小 |
| F-52 | 卡通角色 | 大头、大眼、腮红、天线、摆动四肢，跳跃拉伸/落地压缩 |

## 7. 数值与难度设计

### 7.1 难度曲线

| 距离段（第 N 块平台） | 平台尺寸 | 间隙 | 高度变化 | 无人机概率 |
|---|---|---|---|---|
| 0（起点） | 11m | 0 | 0 | 0 |
| 1–10 | 9m | 2.0–3.0m | ±1.1m | 0 |
| 11–30 | 7–8m | 3.0–3.8m | ±1.1m | 32% |
| 31–45 | 5–6m | 3.8–4.3m | ±1.1m | 32% |
| 45+ | 4.4m（封顶） | 4.3m（封顶） | ±1.1m | 32% |

曲线形态：**前 10 块平台几乎不会失败**（建立信心），第 20 块开始需要连续精准跳跃（进入心流），第 45 块后进入稳定的"技巧区间"。

### 7.2 金币投放

每块平台 1–3 枚，随机分布在平台中线两侧 ±26% 宽度内。刻意的设计：金币不在必经路径的正中央，玩家需要轻微偏离移动路线才能吃到，制造"贪 vs 稳"的微决策。

## 8. 交互与界面

### 8.1 信息架构

```
首屏（开始遮罩）
 ├─ 标题 / 一句话玩法说明
 ├─ 键位提示（桌面）/ 触屏操作说明（移动端）
 ├─ 最高分
 └─ [开始] ← 唯一主按钮

游戏中
 ├─ 左上：分数 / 金币 / 距离
 ├─ 右上：静音
 └─ 底部：摇杆 + 跳跃键（仅触屏）

结算遮罩
 ├─ 本局分数 / 距离 / 金币
 ├─ 历史最高
 └─ [再来一次]
```

### 8.2 关键设计决策

| 决策 | 理由 |
|---|---|
| 开始遮罩只有一个主按钮 | 降低首次进入的决策成本；P2 用户想看的技术信息放在按钮下方一行小字 |
| 数值 HUD 用等宽数字 | 分数跳动时不产生布局抖动 |
| 失败后点击即重开，无加载 | 碎片场景下，"再来一局"的摩擦必须为零 |
| 触屏 UI 只在触屏设备显示 | 桌面端不显示摇杆，避免误触与视觉噪音不必要 |

### 8.3 无障碍与容错

- 跳跃缓冲 + 土狼时间本身就是对操作精度的容错；
- 结算面板不惩罚性文案（不写"你太菜了"），只陈述数字；
- 静音状态可持久化（避免用户每次进游戏都要重新关音乐）。

## 9. 技术方案与约束

| 项 | 方案 | 理由 |
|---|---|---|
| 渲染 | three.js r160（本地化，1.2MB） | 不依赖 CDN，离线/弱网可用 |
| 物理 | 自写运动学 AABB | 需要逐帧可调的参数，用现成物理引擎反而难调 |
| 部署 | GitHub Pages（静态） | 零运维、零成本、全球 CDN |
| 构建 | 无构建步骤 | 改完刷新即可，降低维护成本 |
| 音频 | WebAudio 实时合成 | 无音频文件，包体最小 |
| 存储 | localStorage（最高分） | 无后端 |

**性能预算**：

| 指标 | 目标 | 实测 |
|---|---|---|
| 首屏传输 | ≤ 2MB | ≈ 1.3MB |
| 桌面帧率 | 60fps | 未在真实 GPU 上测（headless 软渲染约 30fps） |
| 移动端内存 | ≤ 150MB | 未实测（v1.1 补） |

**已知技术债**：
1. 无自动化性能回归，靠人工目测帧率；
2. 无错误上报，线上白屏只能靠用户反馈；
3. `main.js` 单文件 1057 行，超过 1500 行就该拆分模块。

## 10. 数据埋点

**v1.0 现状：零埋点。** 这不是疏忽，是范围决策——加埋点意味着引入第三方脚本或后端，与"零依赖"冲突。

**v1.1 最小可行埋点方案**（不引入 SDK，只上报 5 个事件到自建轻量端点）：

| 事件 | 字段 | 用途 |
|---|---|---|
| `session_start` | 设备类型、屏幕尺寸 | 设备分布 |
| `run_start` | 开局时间戳 | 计算单局时长 |
| `run_end` | 分数、距离、金币、时长、死因 | 难度曲线校准 |
| `restart_click` | 上一局分数 | 重开率 |
| `leave` | 停留在 play 状态的累计时长 | 北极星指标 |

隐私：不采集任何个人信息，不上报 IP 之外的标识，不做跨站追踪。

### 14.1 术语

| 术语 | 含义 |
|---|---|
| 土狼时间（coyote time） | 离开平台后仍允许起跳的宽限时间 |
| 跳跃缓冲（jump buffer） | 落地前提前按下跳跃，落地瞬间自动执行的机制 |
| 运动学碰撞 | 直接按速度位移并修正位置，而非用物理引擎模拟力 |
| AABB | 轴对齐包围盒 |

### 14.3 关键数值实测（线上构建）

测试方法：在线上页面注入记录器，每 12ms 采样一次角色高度，分别测量"按住空格 900ms"与"点按 90ms"的最大上升高度。

| 项目 | 长按 | 点按 | 比值 |
|---|---|---|---|
| 起跳基准高度 | 0.55m | 0.55m | — |
| 峰值高度 | 2.68m | 1.74m | — |
| 上升高度 | 2.13m | 1.19m | 56% |

结论：点按/长按的比例 56%，与设计预期（"明显更低但不至于跳不起来"）一致。理论上限 2.33m 与实测 2.13m 的差值来自逐帧积分的离散化损耗，属于预期行为，不修。
